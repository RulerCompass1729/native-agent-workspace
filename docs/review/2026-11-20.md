## A window reconnects a closed service connection by itself

Feedback (the person, 2026-11-20): the daily app showed the local-service-disconnected notice several times within minutes, and each time worked again only after pressing the reconnect button.

Source finding. A window holds one connection per backend. When any one of them closed, the whole window was marked disconnected (`app/workspace-client.cjs`, the entry's `closed` handler), the page was told (`app/main.cjs`, `bindClient`), and only the button's handler connected again, to every backend, followed by a page reload. Nothing recorded which connection closed or why. The running service and backends had not restarted, so the closures were on the connection, not a service exit.

One cause is reproduced, not proven for the reported closures: the service ends a client connection once 1024 frames wait unsent (`app/service-transport.cjs`, `createWriter`), and terminal frames are not coalesced. A main process that stops reading for a few seconds while terminals print reaches that count. Passive sampling of the daily app's socket buffers showed its main process not reading single connections for one to three seconds at a time. Other closing paths remain possible (a state delta that cannot be rebuilt, an oversized or unreadable frame, an encoding failure on the service's side).

Change. `app/service-reconnect.cjs` connects only the closed backend connections of that window again, with the same owner, at 0, 0.5, 2, 5, 15 and 30 seconds, without a reload. The existing notice appears only when this takes more than three seconds and clears itself on success; after the last attempt the button remains. The service is not started by this path, and a backend being updated keeps its own handover. Nothing is sent again: calls in flight on the closed connection fail as before, and operations guarded by the connection revision still refuse. Terminals of the reconnected backend's sessions are rebuilt from a snapshot, because output sent while the connection was closed never reached the window. An agent's hidden window reconnects the same way. Each close and its outcome go to `connection-events.json` in the data directory (private file, newest 200): the backends, which side ended the connection as far as this process can tell (`peer`, a socket error code, `local-destroy`, `state-rebuild`), the longest recent event-loop delay of the main process, attempts and duration. The service's own reason does not cross the socket and is not claimed.

Evidence. `app/tests/service-reconnect.test.cjs` on the previous code: 8 tests, 3 fail, 5 skipped (the window stays disconnected and its page was sent the disconnected notice); on this change 8/0. Full suite 9337 pass / 0 fail. `scripts/test-service-reconnect.cjs` runs the real app hidden against a real service with a synthetic native transport and no model: on the previous code it fails with the notice and the button showing; on this change a closed connection is back without a notice, a four-second refusal shows the notice and clears it without a click, and a main process held for 2.5 seconds while 4000 terminal frames arrive loses its connection (`peer`, event-loop delay about 2500 ms) and gets it back. Draft kept, input count unchanged, terminal output and input continue. Both runs were made while the Mac's screen was locked.

Not verified: the cause of the reported closures in the daily app, which had no record; the installed app; a service that stays unreachable past the last attempt other than by unit test. Not changed: the 1024-frame limit and which windows receive terminal frames. They wait for the new record to show closures with reason `peer` and a long event-loop delay.

## The service's reason for ending a connection reaches the record; a retired hidden window's last minute in the window list

Scope (2026-11-20, added to the record above): two leads joined to the reconnection change. (A) An install pre-check found, in the system's window list of the daily app, an offscreen 1240×850 window that the app's own frames proof did not list. (B) A review of another terminal-reconnect patch (not continued) blocked on two points: a success that arrives after a timeout revives a failed terminal, which then drops later output; and the service's reason for ending a connection never reaches the client.

A, source finding. The app creates windows in three places. One is an agent's hidden background window (`app/main.cjs`, the `context` callback of background control): default size 1240×850, never shown, not focusable, registered in the same statement that creates it. It is opened by an agent's first `workspace_control` call that needs a view, and retired by a sweep every 60 seconds once unused for five minutes (`app/background-control.cjs`, `retireIdle`), unless a call, a delivery or any outbox operation is in flight at that tick. `retireWindow` ends its connections and destroys the window in one synchronous step.

A, runtime observation (read-only sampling of the daily app: the system window list beside the app's frames proof, about 22 minutes). While such a window lived, both lists named the same window id. Two retirements were seen, each at the first sweep after five unused minutes (5 min 54 s and 5 min 14 s after the agent's last call): the proof dropped the window at once, and the system list kept its row for about 63 seconds the first time and about 7 seconds the second. One creation was seen within a second of the agent's next call, with a new id in both lists. The pre-check's failed sample fits this to the minute: the agent's last call before it ended about six minutes earlier, and the sample fell 23 to 61 seconds after the sweep that would have retired the window. So the window was not an unregistered one: it was a retired agent window whose row the system had not yet dropped. Why the row outlives the destroyed window is not verified (one cause that fits is native release waiting for the app's next event). No allowance for the row was added and no daily window was closed or moved.

A, relation to the closed connections. Each agent window holds its own connection to every backend, so the main process reads every state and terminal frame once more per live agent window. That adds to what a held main process has to catch up on; it is not shown to cause the reported closures. The longest main-process pauses sampled earlier did not coincide with a window being opened.

B, late success. This change has no timeout stage in the page, and a failed terminal is never revived in place: output for a failed terminal is dropped by design and only a new terminal built from a snapshot shows the session again. One gap remained: a terminal that failed to load because the window was disconnected (a session on a backend that was not the one reconnected) stayed failed after the reconnection. The page now marks a load that failed with a connection error and builds those terminals again when the window is reconnected (`app/renderer/renderer.js`).

B, the service's reason. The reason cannot travel on the connection being ended, least of all to a reader that has stopped. The service now keeps, per owner, why it ended that owner's connection itself (unsent-frame or byte limit, an oversized or unencodable frame, a failed broadcast, an oversized, unreadable or refused request) and says so once in the ready frame of that owner's next connection (`app/daemon.cjs`, `app/service-transport.cjs`). The client accepts only a known reason and a time (`app/service-connection.cjs`), and the reconnection record names it per backend (`app/service-reconnect.cjs`). Limits: a backend still running an older service says nothing, so its closures stay `peer`; a service that exits tells nobody; only the automatic reconnection records the reason, so a manual reconnect or another connection of the same owner can take it unrecorded; closures decided on the client's side are unchanged.

Evidence. `app/tests/service-reconnect.test.cjs`: 13 tests; on the previous product code 8 pass and the 5 new ones fail; on this change 13/0. They include the real service with two real connections (a refused request and a reader stalled past the unsent-frame limit are told to the same owner's next connection, once, and not to another owner; a connection the client closed or a test fixture dropped is told nothing). `scripts/test-service-reconnect.cjs` (real app hidden, real service, synthetic native transport, no model): three checks pass; the held-main-process check now records `write-queue-frames` from the service, and a connection dropped by the fixture records no service reason. `app/tests/service-boundaries.test.cjs` pinned the exact ready frame; it now expects the reason on the next connection of an owner whose request was refused. Full suite, run while the machine was heavily loaded by other work: 9343 tests, 9337 pass, 5 fail, 1 cancelled. One failure was that pinned ready frame. The other four are in files this change does not touch and wait on real processes for bounded times; those files pass when run alone on the same code (12/0), and the cancelled entry is one of them, whose cleanup did not end after its failure. No green full run exists for the final tree.

Not verified: the installed app; why the system list keeps a destroyed window's row; the reload of a failed terminal in the real app with more than one backend (unit test only).
