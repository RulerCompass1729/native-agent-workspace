## A compacted native turn keeps its NAW authorization when the engine continues it

Branch `lane/claude-compaction-root-20261120`, from main bbbd56fe.

Report (the person: 「这样应该也是 bug」): after an automatic context
compaction in the middle of a turn, every NAW control, operator and message call
of that turn was refused. The agent could do nothing through NAW until the
person typed something.

Measured event order (Claude CLI 2.1.329, isolated profile, a loopback model
fixture, 0 paid model calls): the compaction fires `SessionStart(source=compact)`
and the engine then continues the same turn. The next `turn.step` carries the
same turn id, the next index and origin engine/core. No `turn.start` and no
`UserPromptSubmit` follow. This is the native trace the 2026-11-15 record
"Compact retirement across P0-A and P0-B" listed as not verified.

Finding: the refusal did not come from a gap, an ambiguous prompt, the call
origin, a sub-agent id or a missing tool-use id. The bridge's own compact
handler cleared its active turn, its root prompt and the prompt-to-turn link.
Nothing set them again, because no new turn starts. All three bridge gates then
failed on the missing turn id, prompt id and link. On the NAW side the same
compact retired the live turn and the sharing turn, and the settings hook
reported the session idle while the turn was still running. Reproduced on
bbbd56fe in the native journey: the turn's own read after the compaction
returned the operator-gate refusal and its message returned the message-gate
refusal.

Fix: a capability `nativeTurnContinue`, offered by the bridge and accepted by
the adapter at root binding; never for a retained reader or the compatibility
copy. With it off, behavior is unchanged. With it on:

- At the compact, the bridge keeps a snapshot of the turn, prompt and link, only
  when the turn was active, confirmed and unambiguous. It still clears its gate
  state and sends `control:compact`, so calls stay refused.
- The snapshot is used once, by the engine-core `turn.step` of the same root
  turn id, with the same binding and generation and no gap. A step of a
  sub-agent, of another mod, without an origin, or of another turn restores
  nothing. A new prompt, turn start, turn end, session start or end, or a lost
  observation drops the snapshot.
- On that step the bridge restores its gate state and sends the ordered row
  `control:turn-continue`. The adapter keeps what the compact retired only when
  the capability is on, and restores it only on this row, with the same turn id,
  prompt id and observation epoch, and only if nothing else arrived in between
  (permission or input boundary, another turn row, a gap, a context ending, a
  hook approval, a prompt, a stop failure).
- The adapter restores a new live-turn object. Every root call, outbox proof and
  control scope issued before the compact checks the old object and stays
  invalid; a fresh call of the continued turn mints normally.
- The compatibility copy list gains the bbbd56fe bridge hash.

Not loosened: a call with a sub-agent id, a non-engine origin, no origin or no
tool-use id is still refused in the continued turn. Another session's call is
still refused. Between the compact and the proving step every call is refused.
After the turn ends NAW refuses as before.

Changed boundaries, for the reviewer to judge:

1. The 2026-11-15 record says only a new native turn re-authorizes after a
   compact. Now the compacted turn's own proven continuation also does. The
   test of that record (`compact-control-retirement`, 8 checks) still passes
   unchanged, because it binds without the capability.
2. If a different prompt arrived in the middle of the turn before the compact,
   the bridge gate and the adapter's live turn return as they were before it,
   and the sharing turn stays withdrawn.
3. With the capability on, the settings-hook `SessionStart(compact)` no longer
   retires authority by itself and no longer reports idle in the middle of a
   turn. The ordered compact row, or a declared gap, decides. An idle session
   that compacts still reports idle.

Checks (no paid model call in any of them):

- New `compact-turn-continuation` test, 26 checks, with the real bridge module,
  adapter, workspace and scoped outbox: on bbbd56fe sources 7 pass / 19 fail;
  with the fix 26 / 0.
- Native journey `scripts/test-native-compact-continuation.cjs` (real CLI,
  production host, loopback fixture, one forced compaction): fails on bbbd56fe
  with the operator-gate refusal; passes with the fix, 5 checks, and the session
  state stays working across the compaction.
- Related set, 127 test files: 3,148 pass / 0 fail / 0 skipped. Full unit suite:
  9,017 / 0 / 0, temporary-directory guard 0 before and 0 after.

Not verified: whether an automatic compaction against the online service takes
the same path as the fixture-forced one. A manual `/compact` and an idle
compaction were not traced natively. In the native journey the message call
passed the bridge gate and got NAW's own answer for a session without automatic
messages; staging a real delivery was not exercised there. `workspace_control`
is covered by the unit test only. CLI 2.1.330 was not run. Codex compaction is
outside this change.

Still refused by design: a prompt, permission or input boundary between the
compact and the continuation; another mod wrapping `turn.step`; a call that
races ahead of the `control:turn-continue` row.

No daily app access beyond reading, no installation, merge or push. Independent
review remains pending before integration.

## The compacted-turn refusal seen a third time in daily use: regression and native control evidence

Branch `lane/claude-compaction-root-20261120`, after 91e66f74. This record adds
to "A compacted native turn keeps its NAW authorization when the engine
continues it" above. No product source changed; the test and the native journey
did.

Report (queue item, 2026-11-21 UTC): in a daily session on Claude CLI 2.1.329,
in bypass permission mode, one turn made three queue control calls that NAW
answered. The context then compacted automatically. The same turn went on: same
prompt id, no new user message, no turn end in between. Its next
`workspace_open` returned "Operator calls require this confirmed native root
turn and its unambiguous prompt." and its next queue `workspace_control` call
returned "Background control requires the actual native root call." The
following turn, started by another message, worked. Read from that session's
own transcript, read-only.

What this shows: the automatic compaction of the online service produces the
same outward order as the fixture-forced one (a compaction in the middle of a
turn, then the same turn and prompt continue), and the two refusals are the
operator-gate and control-gate texts of the bridge. What it does not show: the
bridge's internal state in the daily app was not traced, and the fix has not run
in the daily app.

Added regression (`compact-turn-continuation`, now 27 checks): the daily
sequence with the real bridge module. A queue control call is taken before the
compact; after the compact `workspace_open` and a queue-add control call get

- On bbbd56fe: fails. After the compaction the same turn's read gets the

  `caller-unavailable`, because this fixture has no space transport. The root

  so a missing live turn would have answered `native-call-invalidated` instead.

## Two more daily occurrences read as acceptance samples; a display gap before the compaction stays NAW's answer

Branch `lane/claude-compaction-root-20261120`, after f4ab377e. This record adds
to the two records above about the compacted native turn. No product source
changed; one check was added to `compact-turn-continuation`.

Report (queue item, 2026-11-21 UTC): a fourth refusal after a compaction, to be
an acceptance sample of the fix. Read from the same daily session's own
transcript, read-only (Claude CLI 2.1.329, bypass permission mode). The queue
item places it about forty minutes earlier than the transcript's timestamps; the
transcript is used here.

Fourth occurrence: a turn the person started by typing. NAW answered its control
call and its session listing. The context then compacted automatically and the
same turn went on under the same prompt id. Two queue-add control calls returned
"Background control requires the actual native root call." and three
`workspace_message` calls returned the message-gate refusal
「没有本原生主会话的定向协作授权。」. The next turn sent all five again and NAW
took them. Compared with the third occurrence: the person started this turn,
not a workspace message, and the message gate is seen refusing in daily use for
the first time.

Checks that already cover this shape, so nothing was added for it:

- `compact-turn-continuation`, "the engine's next step of the compacted root
  turn gives it back control, operator and message calls": between the compact
  and the turn's next step the control and message calls get exactly these two
  texts and nothing reaches NAW; after the step both pass. It fails on bbbd56fe.
- The "daily sequence" check of the record above makes the queue-add control
  call by name.
- The native journey: after the compaction the same turn's control call and
  message get these two refusals on bbbd56fe, and pass the bridge with the fix.

Fifth occurrence, in the same transcript about twenty minutes later: not a pure
compaction. In one turn NAW first refused a `workspace_open` with "The current
native Claude root turn and prompt are not confirmed" and answered three queue
control calls `unconfirmed`, `native-call-invalidated`, check `display-gap`.
These are NAW's own answers, given before any compaction. The turn then
compacted automatically, and its next queue-add returned the bridge's
control-gate refusal.

What the fix does in that order, read from the source: a declared gap clears the
live turn and any kept compacted turn and sets the display gap; the compact row
then finds no live turn and keeps nothing; the continuation row restores nothing
while the display gap stands. A bridge that lost nothing itself restores its own
gate. The call therefore reaches NAW again and gets NAW's display-gap answer, the
same as before the compaction. That turn still cannot use NAW until a new turn
starts. Why NAW declared the gap in the middle of a turn is a separate, open
investigation and is outside this change.

Added check (`compact-turn-continuation`, now 28): "a turn NAW holds a display
gap for gets NAW's same answer after its compaction, not the turn back". The
fixture's control stub now answers a refused root call as `claude-submit.cjs`
does, with the failure reason and check, so the check can compare them. On
bbbd56fe sources: 7 pass / 21 fail, and this check fails with the daily pair in
the daily order: `unconfirmed`, `native-call-invalidated`, `display-gap` before
the compact, the bridge's control-gate text after it. With the fix: 28 / 0.

Acceptance in daily use, once installed: in a turn that compacts with no gap
before it, a call after the compaction must not return any of the three bridge
refusal texts. In a turn where NAW had already answered `display-gap` before the
compaction, the same answer after it is expected and is not a failure of this
fix.

Not verified: the fix in the daily app; the internal state of the bridge and of
NAW in these two occurrences (only the transcript was read); whether the bridge
itself had lost observation in the fifth occurrence. If it had at the compact,
it keeps no snapshot and its own refusal text stays until the next turn. The
full unit suite was not run again: only this test file changed.

Independent review remains pending before integration.
