## The review record is one file per day; docs/review.md is frozen (2026-11-13, Claude 2)

**Why.** The push guard (`scripts/privacy_guard.py`, `MAX_BLOB`) refuses any
single file over 2 MiB. On main, `docs/review.md` was 895,734 bytes after the
last commit of 11-10 (3adba67d), 1,377,391 after 11-11 (326a160a), 1,521,229
after 11-12 (25fd89d3) and 1,631,140 at 42a122ad (11-13, midday), so a push
would have been refused within about two days. Every edit also added a whole
copy to history: 934 distinct versions reachable from main, 643.1 MiB, about
half of a full-history scan. The guard's limit is the person's hard gate and is
not changed here.

**Change.**
- New records are appended to `docs/review/YYYY-MM-DD.md`, one file per day by
  `date +%F` on this machine. A day at the recent rate is a few hundred KB, so a
  day file stays far below the limit and each edit adds a small version to
  history.
- `docs/review.md` gets one paragraph at the top pointing here; nothing in it is
  removed or changed. It is frozen as main had it at ee808a73 (1,635,857 bytes,
  1,636,090 with the paragraph). A correction or status change to an entry there is a new
  record in that day's file, naming the entry.
- CLAUDE.md: the three places that told agents to write `docs/review.md` (the
  reviewer brief, recording a reviewer's findings, the evidence rule) now say
  "the review record", and a new rule says where it is, that `docs/review.md`
  is frozen, and how to merge (below). README's document map points to
  `docs/review/` and to the earlier records.
- References that cite something already in `docs/review.md` are unchanged:
  `docs/{alpha,architecture,core-milestone,interaction,live-progress,product,readiness,testing}.md`
  and a comment in `scripts/test-native-tools.cjs`. Each points at an entry or
  row that stays in the frozen file, and its first paragraph points here.
  `docs/core-milestone.md` also says to keep findings "in the existing
  `review.md`"; that instruction belongs to the alpha.23 increment, closed on
  2026-10-18, and is left as written.
- `app/tests/docs-size.test.cjs` (full suite) fails when `docs/review.md`
  differs from its frozen copy (sha256) or is missing, and when any other file
  under `docs/` passes 1.5 MiB. Checked to fail: one byte appended to
  `docs/review.md`, one byte changed in place (same size), the file moved away;
  a day file and a top-level docs file each one byte over 1.5 MiB. A day file
  of exactly 1.5 MiB passes.

**Merging.** Lanes started before this change may still add to
`docs/review.md` until they are based on it. An addition at the end, or an
edit inside an old entry, merges without a conflict; an addition at the top
conflicts with the new paragraph. In each case the test then fails. The
integrator restores main's frozen `docs/review.md`, puts each added record,
and each change restated as a record naming its entry, at the end of the day
file of the day it is moved, and keeps every record when two branches add to
the same day file.

**Left open.** The versions already in history stay; a full-history scan still
reads them. Finding an issue's latest status or the next free ID now means
searching `docs/review.md` and `docs/review/`. A lane reads the rule only from
its own worktree's CLAUDE.md, so lanes on older bases learn it from the board
or when they rebase; the test catches what they add meanwhile.

## The push scan in gitleaks batches, total bound 2 GiB (privacy guard, 2026-11-13, Claude 4)

From the person's approval (about 15:30 PT), with their words 「隐私扫描不管怎么改,不能出问题」:
a push of main was blocked because its complete-history scan needed 1,183 MiB,
over the 512 MiB bound; the guard handed all of it to one gitleaks run.

**What changed.** `scripts/privacy_guard.py`: `MAX_SCAN` is 2 GiB and
`MAX_BATCH` 192 MiB. `Scanner.add` runs every check on each part as before,
then sends the current batch to gitleaks (`flush`) when the next part would take
it past `MAX_BATCH`, so a batch is cut only between whole parts and memory holds
one batch. Each batch keeps the 120 s tool and 135 s process deadlines. A batch
passes only on exit 0 with an empty JSON report (`--report-format json`); a
timeout, another exit, a missing or unreadable report, or a reported finding
blocks. `finish` sends the last batch and blocks unless the batches together
hold every accepted part and byte once. One stderr line per batch in a scan of
more than one; the PASS line names the batch and part counts.
`docs/publication.md` records the change.

**Tests and checks.**
- Guard suite 37/0 (`python3 -m unittest -v tests.test_privacy_guard`, 201 s).
  New: batches cover every part once and end at part boundaries; a secret and a
  private record in the first, middle and last batch and on both sides of a cut
  (a secret fails in exactly the batch that holds it, after earlier batches
  pass); history across batches with a secret or private record in a message,
  a personal handle or a personal email as author and as committer, and the same
  history split small and unsplit gives gitleaks identical input; a timeout,
  an error exit, no report, an unreadable report or a reported finding in the
  second of three batches blocks and no third batch runs; a gitleaks that exits
  0 without a report blocks a real commit. The total-bound test runs the same
  check at 3 MiB and pins the constants.
- The seven new or changed tests are red on the previous guard (main 5496cbf9).
  Nine mutations of the new guard are each caught: the last batch never sent,
  the same with the coverage check removed, a batch sending only its last part,
  exit codes ignored after the first batch, the report not checked, a timed-out
  later batch skipped or counted as passed, the batch bound checked after
  appending, and the total bound removed. With exit codes ignored, the report
  check still blocks; with a skipped batch, the coverage check still blocks.
- Same history, both guards (the public origin/main, 544 commits, real rules and
  gitleaks): the same verdict, 4,058 blobs, 177,092 parts; the former guard in
  one 260.7 MiB gitleaks run (85.8 s), the new one in 191.9 + 68.8 MiB (64 s +
  23 s); the joined gitleaks input has the same SHA-256 (273,317,763 bytes).
- The real bounds on synthetic 2 MiB parts, gitleaks replaced by a clean
  stand-in: 1,024 parts (2,147,475,456 bytes) accepted, of which 960 went to
  gitleaks in 10 batches of 192 MiB; the next part then blocks as over 2 GiB,
  so the last 64 were never sent.

**Left open.** gitleaks reads each batch alone, so a match that needs text from
both sides of a cut (the end of one part and the start of the next, which are
different files, patches or messages) is no longer possible; a secret inside one
part is always whole within one batch. A batch near 192 MiB took 64–70 s in
measurements, inside the 120 s deadline on this machine; a slower machine can
still time out, which blocks.

## A bottom-slot panel no longer squeezes the session list (2026-11-13, NAW dev (continued))

From a queue item: with a panel plugin installed in DSH's bottom slot and
expanded, NAW's left column kept its fixed rows (about 237 px above, 70 px
below) and the session list took the whole loss, so the first session card
showed 13 px and the others none.

**Cause** (source). The pinned DSH frame
(`@deepseek-ai/dsh-client-ui-layout/lib/client.js`) is a grid with rows
`minmax(0,1fr) auto`; the bottom slot (`[data-shell-bottom]`) spans
`grid-column:1/-1`, so all three columns shrink by its height, as DSH's README
says. NAW's sidebar gives the shrink to its flexible part
(`app/renderer/sidebar-layout.js`).

**Change** (`scripts/build-ui.cjs`). Two global rules after NAW's styles: the
grid child that holds NAW's sidebar surface spans `grid-row:1/-1`, and the
bottom slot beside it spans `grid-column:2/-1`, as an editor's bottom panel sits
beside its navigator. With no occupant the slot is 0 px tall and nothing moves.
The build throws "requalify" unless the frame still has that row template once,
the bottom slot's `grid-column:1/-1` and one `data-shell-bottom` marker.

**Checks.**
- `app/tests/sidebar-bottom-slot.test.cjs` (6): the built styles carry both
  rules and NAW still registers its `sidebar` surface; four frame changes each
  fail the build (bottom slot not full width, another row template, the marker
  renamed, a second marker). Five are red on main's builder (d1acb9ff).
- Full suite 6769/0.
- Hidden real window, synthetic transport, fresh profile, three sessions, no
  model; the real panel plugin unchanged. Window 1240×850, before → after:
  panel expanded (266 px), session list 14 → 175 px (Chinese) and 10 → 171
  (English), cards 13/0/0 → 52/52/52 (48 each in English), all three hit
  themselves; collapsed bar, list 158 → 175. Narrow 850×600 (rail), panel
  expanded: list 0 → 120, the same as with no panel (the rail's third card is
  cut with no panel too, unchanged here). Message area, reply, input and
  terminal heights unchanged; new session and settings reachable in every state.

**Trade-offs.** At the default width the panel is 280 px narrower (960 of
1240). DSH's sidebar width handle covers only the upper row, so it stops at the
panel's top edge when the panel is open. Any later bottom-slot occupant gets the
same placement. Alternative kept in reserve: a full-width panel and a sidebar
that scrolls with a minimum list height.

**Open.** This changes how the window looks, so it waits for the person to see
the before/after pictures (private: they show the plugin's data) and agree; not
merged or installed. It overrides the pinned DSH frame layout across modules, so
the integration batch takes it to independent review.
