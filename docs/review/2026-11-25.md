## Copy the DSH runtime in a process of its own

An update makes a new backend, and startup copied the DSH runtime to it before the new backend became active. On the day this was written that copy was refused at its two-minute limit on a busy disk. The update itself succeeded, but the new backend stayed without DSH until NAW was opened again, because only a start tries again. The copy also ran in the window's main process, so a busy window slowed it, and an installer had to wait for all of it.

The copy now runs in a child process (`app/dsh-copy.cjs`, the app's own executable as Node, like a backend). A start waits for it at most 120 seconds and then goes on: the new backend becomes active, the window opens, `services.lock` is released, and the copy continues. It stops after 30 seconds in which nothing finished or after 30 minutes. A failed copy is recorded and tried again after ten minutes, from the source after it, at most twice per run; a copier that ended without a verdict is tried again without a record, because it says nothing about the source. A copier holds its own lock in the target backend, so a second one neither clears a live half directory nor copies beside it; it waits. It ends when the process that started it ends, and the next copier clears the half directory. The source, ownership, permission, link, size, count and pre-publication checks are unchanged; the empty reservation and the rename that publishes are now in one turn, so a copier that ends with its window cannot leave the reservation, which every later copy refuses. Clearing a half directory has the same limits as copying, because a half directory of a full runtime is now an ordinary case.

Smaller than the plan: there is no separate stall watchdog, since the copier's own 30-second check is in a process nothing else keeps busy; and the rule that keeps an empty backend while its runtime is wanted already covers a copy in progress, so it is only tested.

Red on the earlier code: a copy whose steps move but which takes over two minutes never appears without another start; with 30 ms of work in every turn of the caller's event loop the copy took 6,234 ms against 622 ms idle. Now it appears by itself with its record cleared and `services.lock` free, a second start begins no second copy and keeps the empty source's backend, and the busy copy takes 123 ms against 113 ms. Further tests cover a background stall followed by the next source, the number of tries, a killed copier, an executable that cannot be started, two copiers, a killed parent, a layout that changes between tries, and a record that waits for another start's lock. An isolated installer run (synthetic bundles, real backends, hidden, `dsh-slow` in `scripts/test-installer-failures.cjs`) with a copy of over four minutes: installed, the window's start ended without DSH, DSH appeared 135 seconds later, no model call and no dispatch. Of thirty mutations of the new lines one is not caught: without its `error` listener a child that cannot be started still reports `close`, so the listener only prevents an uncaught error. The related files gave 1,320 of 1,321; the one failure, in `app/tests/install-state.test.cjs`, is the same on the earlier code.

Not checked: a hung disk read inside one system call, which no limit in that process can end (the next start does); a corrupt copy lock, which a copier waits 30 minutes for, as `services.lock` refuses; a full-size runtime on the maintainer's disk; and the daily app. A dialog for a new session that is already open shows DSH only after it is closed and opened again or a choice in it changes; the window and NAW need not be reopened. This is read from the source, not run.
