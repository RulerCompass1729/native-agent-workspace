## Butler wakes for refusals: past one record page, and after a release (288, follows the 287 review)

Source: two non-blocking items from the 287 review, which the project manager sent for repair.
- (1) The check for refusals read one page of the record, at most 100 events or about 8 KiB. A longer cycle counted as news, so more than 100 refusals between wakes woke the butler every minute with no limit.
- (2) Only a call of the butler's that went through reset the count. If the person released the butler from the card, refusals after that did not wake it.

Fix (0b3f6f14):

- A release the dispatcher confirms now resets the count. That release is either the person's from a window or the butler's own. A refused, outdated-backend or unconfirmed release resets nothing.
- Unchanged: the limit of 3, the 60 s interval and every refusal condition.

## Migration quiet window: NAW stops new work on a backend that waits only for quiet, for a bounded time (288, else 289)

Source: the project manager's dispatch, approved by the butler. When a migration plan is ready, `migrate` is on and the backend waits only for its sessions to be quiet, NAW opens a window with a deadline. In the window it sends no new item and holds automatic messages. The move runs once the running turns end and the existing quiet rule is met. At the deadline the window closes, held messages are sent again and a reason code goes out through the VersionEvents exit. No UI is wired, and conflict 3 (waking the sender after delivery) is not built.

Change (f42fd625, a04169d8, 3031f476):
- `app/quiet-windows.cjs` (new) is the record in the GUI data directory. A window opens only when `moveWait` reports quiet-10m, quiet-30m or busy. The deadline is 30 min plus the quiet rule, at most 60 min. There is no reopen for 2 h after a timeout or not-waiting, also across a restart. A window past its deadline is void at start. The reader refuses links, other owners, modes other than 0600 and oversize files.
- `queue-dispatch.cjs`: `sessionReady` returns `quiet-window` for the window's sessions, and every start path reads the marked view.
- `session-wake.cjs` holds automatic messages to a windowed backend, at most 32 per sender backend. They are checked every minute and sent once the window closes, re-addressed only to the same native session after a move.
- `main.cjs`: `autoBackendSwitchOnce` opens and closes windows, and a timeout emits `quiet-window-timeout` once through VersionEvents.
- `steward-wake.cjs` records the butler's blocked reason. `ui-messages.js` has the zh/en text. The module is added to the package and the backend runtime copy. `moveWait` is injected from main, so the runtime copy needs no dispatcher modules.

Tests (no model calls):
- Red: 17 of 19 fail on 1051d64f.
- The two new files pass, 21/21.
- The related sets (251 files) give 5476/5477. The one failure is install-state "Runtime link escaped" under a short /tmp TMPDIR; it is 25/25 with the default TMPDIR.

Independent review: headless Opus with read-only tools, one session, three passes.
- Pass 1 failed on B1. A message between two sessions on the backend being moved was promised a resend, but the move ended that backend's store and the held row was cancelled or dropped. Fix a04169d8: such a message is refused at once with an honest reason, both at registration and at turn end. The new test fails on f42fd625 and passes after the fix.
- Pass 2 passed, and settled N8: rotation successors are created on the active backend, which never gets a window.
- Pass 2 also found one more gap: a row held for the butler's 60-second limit just before a window opened was sent into the window at its retry. Fix 3031f476: every retry and turn end checks for a window (`keepQuiet`), and the same-backend wording was tightened as the reviewer suggested. The new test fails on a04169d8 (2 sends vs 1). Pass 3 passed.
- Non-blocking items are accepted as limits:
  - an install fails closed while window-held rows exist;
  - an expired-at-start window does not start the 2-hour pause;
  - a forged same-user record holds messages for at most 2 h;
  - an unreadable record means no hold;
  - `busy` covers a question to the person;
  - a sender told a butler-hold time is not told again once its row becomes window-held.

Not verified: the daily app and a real backend migration. Every check is synthetic.

## Butler's own-handoff hold: a failed pass, and a banner that named a missing menu item (289, follows the f77f4d45 review)

Source: rows #2 and #4 of the non-blocking notes from the later review of f77f4d45. Row #6 (the banner's wording) gets a zh/en prototype for proxy review first, so this record covers no wording change.

**Findings, reproduced.**
- #2: a failed pass during a hold called `skip()`, which replaced the hold's reason but kept its step.
  - After 10 minutes it wrote a second record line, and the next hold wrote a third.
  - When nothing was due it cleared the hold, so the banner disappeared and the next hold started over with a new record line.
- #4: with step `update-backend` and no menu item for it, the banner fell back to text naming 「结束并更新这个后台…」. That item's visibility comes from the backend version notice, a different source from the step, so the two can disagree and the person is pointed at a missing item. The step button from 5847b1f2 covered only the case where the item exists.

**Fix (fcd00f97).**
- `steward-wake.cjs` `skip()` returns at once while a hold is set. A failed pass reads nothing new; every successful pass reaches `hold` or `endHold` before any `skip`.
- `renderStewardWakeWarning` always uses the step's own sentence, which names no menu item. The button appears only when the sidebar menu has that item.
- The fallback strings `stewardWake.ownHandoff.release`, `.update-backend` and `.action` (zh and en) are removed. They have no remaining references.

**Tests (no model calls).**
- Red on 311e3265: 3 of 15 fail. The not-due branch of the new hold test fails separately on the old `skip()`.
- Green: 62/62 in the steward test files. The related sets (233 files) give 1855 + 830 + 1179 + 831 tests, 0 fail.

**Independent review.** A fresh headless session with Read, Grep and Glob only and no MCP servers. PASS, no blocking findings. HEAD, index and worktree were unchanged. Non-blocking notes:
- A read failure during a hold is not recorded, and the banner keeps the hold until a read succeeds.
- When the step and the menu disagree, the person is still given no working path. Showing the menu item from the server's version check is left until such a disagreement is seen in use.
- The `wakeSteward` catch during a hold has no test of its own; the guard is inside `skip()` itself.
