# pi on DeepSeek: the gate in the private runtime copy (R246)

Continues `docs/review/2026-11-25/pi-tui-20261125.md`.

## Finding at integration (alpha.311, 2026-11-26 00:54 PT)

The integrator, reading 41caa36b while merging it: the service runs from the runtime copy that `app/service-client.cjs` makes from its `names` list, and `pi-tui.cjs` reads its gate from `path.join(__dirname, 'pi-confirm.mjs')`, which the list did not name. In daily use a pi start would fail reading the gate (the gate is not bypassed). The tests load `app/` directly, so none caught it. `scripts/package-mac.cjs` already packages the file.

## Fix

- `names` lists `pi-confirm.mjs` after `pi-tui.cjs`.
- `app/tests/service-runtime-closure.test.cjs`: copies the runtime by the list, walks from `pi-tui.cjs` through local `require`, `import`/`from` and `path.join(__dirname, '<file>')`, and asserts every file reached is in the copy; then calls the copy's `prepareHome` and compares the written gate with `app/pi-confirm.mjs`. The two tests share one copy, since `scratch.release()` runs once per process (a first version with a copy per test left one temporary folder, reported by the runner's temp guard).
- The walk starts at `pi-tui.cjs` only. From every listed file it also reaches `butler-dsh-launch.py`, `butler-dsh-host.mjs` and three `butler-dsh-*.cjs`: the functions that read them are called from `main.cjs`/`butler-dsh-driver.cjs`, which run from the bundle, not from the copy (source reading, not run).
