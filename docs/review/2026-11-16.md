## PF07 — distinguish a failed standing reservation from an unknown operation result (Codex B)

Source: the assigned PF07 follow-up to the standing-permission review. On the designated main baseline `96b56e89`, a standing usage reservation could throw before any application handler entered, yet the generic catch recorded `unconfirmed`. That incorrectly prevented a caller from safely retrying work that had never run.

`BackgroundControl.perform` now recognizes only the exact exception from its standing-policy callback, provided neither this execution nor a prior resumable handler entered. It settles that operation as `not-executed`, with reason `standing-authorization-unavailable` and an explicit hint to retry with a new operation id after storage recovers. The same id remains an immutable receipt and never replays. Errors from the handler, delivery and final audit retain their existing uncertain-result behavior. No general pre-execution-error reclassification or exception-message matching is introduced.

The policy, permission comparisons, designation, confirmation gates and hourly allowance are unchanged; PF08 is outside this patch. Even if the usage write succeeded before its acknowledgement failed, the operation remains unexecuted and the reserved usage is not refunded. Operation-record/audit storage failure paths otherwise remain conservative.

The new permanent regression uses the real `StewardStanding`, `BackgroundControl` and `RoomState`, with an actual missing-parent filesystem write failure in an owned temporary store. It covers join/create/archive, durable failure receipts across restart, same-id non-replay, successful new-id retry after recovery, and a durable reservation whose later write acknowledgement fails. Controls produce the same storage failure after handler entry, and fail the final audit after a completed effect: both remain unconfirmed and never replay across restart.

## PF08 — require current native cost observations for standing creation (Codex B)

**Finding.** This can bypass the intended configuration confirmation, rather than only add an extra card. The real Claude adapter and Workspace update the displayed model when an ordered native model block arrives, so that normal path was already current. However, a later-arriving startup hook can overwrite the effort scalar with its older launch value. The regression first observes native effort `high`, delivers a late startup effort `low`, then requests `low`: the old policy executes without a card despite the newer native observation. Startup-only values, stale observations, gaps and replaced contexts could also remain eligible without any freshness check. The reverse direction can conservatively ask for the actually current effort.

**Repair.** Claude now keeps separate in-memory creation observations. A live, ordered, non-replayed native model block supplies model authority; an explicit non-startup root settings hook supplies effort authority. Startup values are not promoted to this authority. Workspace projects those observations only while the runtime is alive, ready and bound to its current native identity, observer epoch and input-control revision, with no observation gap. A gap clears the evidence. These timestamps and observations are ephemeral, not restored launch settings or a new persisted permission.

For each explicitly requested model/effort, `creationCovered` requires the exact matching observation from the same permission-baseline peer, a matching native identity/control revision, and an age between zero and **60 seconds**. Unknown, expired, clock-rollback or invalid evidence requires the existing human card. The policy rechecks its own clock and observations after the running audit; a change or expiry there prevents the handler through the existing revocation path. Omitted values retain the previously approved provider-default semantics. Codex creation, permission comparisons, actor designation, directory constraints and hourly allowance are unchanged. No new polling, provider API or model call is introduced.
