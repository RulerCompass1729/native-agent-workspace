## Give a delivered handoff turn its own time limit

A rotation waited two minutes for the successor's first turn to complete. A successor still working after that was stopped, its work returned to the old session and the old session was not rotated again for seven days. Of 125 recorded rotations, 13 first turns took longer than two minutes (median 0.6, longest 13.3). Rotations that the limit had ended are not in that sample, so it does not show that thirty minutes is always enough.

Delivery keeps the two-minute limit. A delivered turn has thirty minutes from the handoff, waiting for the person included. A successor known to be ended, backgrounded or recoverable keeps two minutes. A disconnected one or one out of view has thirty. Failed, interrupted and incomplete turns still roll back at once. The confirmation rule, the guards before a stop and the place of open decisions are unchanged. The wait for running collaborations starts at the confirmed turn.

The first 18 tests had 10 failures on the earlier code and pass on the change. The other eight guard behavior that must not change. Eight mutations of the change each fail at least one of them. Two failures in a wider run came from a temporary folder inside a repository. Those two files pass with the system temporary folder. No native provider or model was called by these tests.

Independent review found that a failed write of the delivery record stopped the successor without the guards of a failed handoff. Two tests reproduce it and pass with the fix. The same reviewer accepted the delta with zero blockers. Remaining limits: one rotation runs at a time, so a stuck first turn can hold the others, and the butler's wakes, for up to thirty minutes. If the delivery record was never written, the app was reopened and the successor stays out of view, the two-minute limit applies as before.

A space record cannot be deleted in the product, so a failed rotation's cleanup does not depend on one that is gone. An archived space completes its cleanup and the record expires.

## Let a slow DSH runtime copy finish

Startup copies the DSH runtime to the new backend and stopped it thirty seconds after it began. Two daily starts lost DSH that way, and each cost the person an approved reopening. The record kept the reason but not where the copy was.

The copy now stops when nothing has finished for thirty seconds, or at two minutes in total. A finished entry, directory, file, link or 128 KiB piece of a file counts. Clearing an interrupted copy and checking a runtime already in place keep their thirty seconds in total. No ownership, permission, link, size or count check changed. A refused copy records its stage, the items finished in that stage and the elapsed time in the startup layout. Rows without them stay valid, and alpha.296 and 297 read rows with them.

Startup finishes the copy before the new backend becomes active, and the installer waited sixty seconds for that. A copy between one and two minutes would have turned a missing DSH into a failed installation, so the installer now waits 210 seconds at most and still returns as soon as the backend is active.

The new inheritance tests slow single operations on an injected clock, except one that injects an open error. Those for slow files, one large file, a slow inventory, directories, links and the last checks failed on the earlier code with the thirty-second deadline.

Independent review found three blockers: an installer failure test killed the installer after 180 seconds, synchronous metadata reads had not been measured, and this record had inaccurate sentences. The installer failure test now allows 300 seconds and was not run. A walk now yields after 50 ms as well as every 128 entries, each runtime check counts as progress, and the clearing limit has a test. Six mutations of the change each fail at least one test.

Real runs on synthetic trees: with every source open delayed by 280 ms the earlier code stopped at 30.1 s and the change finished in 42.8 s. With every `lstat` of a source entry blocked for 20 ms the longest event loop hold went from 3246 ms to 99 ms, for 5 ms from 814 ms to 62 ms. The three runtime checks in a copy are still synchronous and do not yield; this probe did not slow them. Without a delay 70,000 files took 5.8–6.6 s on both in seven of eight runs before the yield was added; one run of the change took 58.9 s, no cause found, and finished. Ten later runs on a loaded machine took 7.0–13.7 s on the earlier code and 8.7–11.5 s on the final change, too noisy to tell apart. The added clock reads cost about 17 ms over a whole copy.

Two minutes is a chosen limit, not a measured one. The window with sessions still opens only after the copy: a start can spend 30 seconds clearing an interrupted copy and 120 seconds copying from each source it tries, where the copy had 30. Reconnecting a page can copy too and holds the startup lock as long. One file operation that never returns is still not interrupted, as before. A failed copy is tried again only by the next start or reconnection.
