# 待你确认接入铃铛：实现候选与验收边界

## 当前迁移状态（2026-11-16）

用户已批准原实施图；本候选仅在新 main 上移植，等待独立增量审与集成，不代表已安装。下文原方案与原审查记录保留为设计背景。

桌面、手机提醒与推送共用唯一 `appRecordsStatus`，当前绑定 client 随每次计数调用传入；已删除上次手机读取 client 的缓存。临时提醒故障回退保留 main 的行为，稳定清理快照保留 ticket。原执行 fingerprint 已抽为共享函数，其内容保留当前 main 后加的维护作用范围判断。

提醒摘要继续走白名单。main 已有的手机确认授权是独立路径：只有原控制器对完整原卡提供匹配的展示证明时，才保留原正文与版本供现有授权流程使用；提醒摘要仍重新白名单化。完整卡 ID 用当前 native 身份定位，不猜不透明 operation ID 的分隔符，歧义拒绝。原 read scope、服务绑定、版本、到期及决定时授权门继续保留。


问题：用户从任何视图都能找到仍有效的确认请求，点列表行回到原卡；铃铛数字表示有效待确认卡与当前待处理提醒之和。

现有机制：`record-reminders.js` 管铃铛；`main.cjs` 的 `displayState` 向人的窗口投影 `backgroundConfirmations`；`activity-stream.js` 已通过原卡标识导航。

最小增量：在同一个铃铛内接入同一个确认来源，补齐历史状态与列表摘要，不另存一份确认队列。

不做会坏什么：确认卡仍散在会话中；铃铛计数若沿用记录提醒数，会让人把无效请求或清理提醒当成待确认。

服务愿景「一个入口，用好所有 agent」：需要人判断的事集中可找，进入正确原卡，不让人反复寻找会话。

## 一个来源、两种筛选

来源仍是 `BackgroundControl` 的同一份操作账本、现有状态和 `backgroundConfirmations` 人用投影。铃铛、原等待条以及 E 的手机读取侧复用同一个投影契约；不建立新的持久文件、第二套到期定时器或浏览器私有的授权状态。后台执行仍走原 `decide`、身份/前提重核和条件输入出口，列表跳转不调用确认或终端输入。

上一单 `86545eab` 的 `pending()` 只投影仍待确认、未到期、未被新卡取代的卡，不能直接充当「全部」。实施时先搜索并迁移所有 `backgroundConfirmations` 消费者，在来源层统一补出可见记录及是否可处理；保留原字段，新增状态/到期/摘要等字段。原等待条和铃铛使用同一个后台给出的可处理集合，历史筛选使用同一账本的投影；不能让一个消费者把新加入的历史行按数组长度误算成待确认。

实现契约：`BackgroundControl.confirmations()` 是来源；`confirmation-inbox.cjs` 是铃铛计数和手机白名单；执行和投影共用 `background-fingerprint.cjs`。

| 内容 | 规则 |
| --- | --- |
| 身份与定位 | 保留 `id`、`operationId`、`sessionId`、`nativeId`；原卡 ID 含原生身份，不能仅按请求标题或 operationId 搜索。 |
| 列表摘要 | 发起者、目标可见名称、操作的人话摘要、创建时间、到期时间、状态/原因 key；不向手机透出原始命令参数、终端内容、native approval 内容或后台 guard。 |
| 有效集合 | 只含后台确认仍可处理的请求；过期、失效、撤回、取消、已完成、被取代均不计数。不确定或暂无法核对的请求不能冒充已核实可执行，保留在「全部」并写明原因。 |
| 全部 | 同一来源中的确认请求历史，状态和原因保留；不把普通后台操作都混入。若需分页，游标和历史完整性也由同一来源提供，不静默截断。 |
| 时间 | 等待时长由创建时间显示；剩余时间由到期时间显示。终端输入两分钟、其他十分钟沿用上一单，不在 UI 另定 TTL；确认当下的后台期限为准。 |

有效集合复用既有 `checkTerminalInput` 和执行 fingerprint，但窗口快照可能落后。目标缺失、身份/归档/状态或前提不吻合时，投影只排除计数并显示「无法核实」，不据此永久作废卡，也不声明目标已消失。新快照可恢复同一张卡。真正执行仍在原 `decide` 重核，TTL 在原到期出口收口；门未放宽。到期写盘失败在统一投影中降为无法核实，读会话不重复尝试写盘；原会话和已确认历史继续可读。不要在铃铛复制判断或直接改账本。


## 接入和交互

1. 复用 B 的 `records-button` 和铃铛容器，从会话、空间、总览、终端与空状态均可找到。数字 N = 有效待确认卡数 + 当前显示、等待人处理的记录提醒和临时目录提醒数。待确认独立一节放最前，其余提醒另节，保留既有操作。此规则替代旧方案中「提醒不能加进 N」。
2. 默认「待确认」，可切「全部」。每一行显示发起者 → 目标、动作、已等多久、还剩多久或已结束状态；排序稳定，按创建时间从早到晚。列表使用原生按钮和真实列表语义，长名称换行而不挤掉状态。
3. 点行关闭铃铛并复用 `host.confirmation({sessionId,nativeId,messageId})` 的原卡导航。确认/取消在原卡处理，避免在新列表再做一组执行按钮。会话或原卡不可定位时清楚显示原因，保留摘要，不新开 agent、不重放请求、不清空草稿。
4. 后台账本变化通过现有状态更新推动列表与计数；窗口无待处理项时无每秒刷新。打开列表时一个显示时钟更新年龄/倒计时；关闭、到期及组件销毁时停止。倒计时不做每秒屏幕阅读器播报；原生 dialog 的焦点进入/退出、Esc 关闭和键盘逐行操作均需实测。
5. E 的手机侧消费同一状态/有效性字段，只适配宽度与导航；本单不另实现手机布局，不新增 agent 的确认权限。

## 与已同意原型的差异，实施图须逐项展示

| 原型 | 当前派单下的实施要求 |
| --- | --- |
| 「待确认 / 已处理」 | 改为「待确认 / 全部」，可查过期、失效、撤回及其他结束状态。 |
| 只有「20 秒前」等年龄 | 同时给等待时间与剩余时间，沿用已定 TTL。 |
| 列表内有确认、取消按钮 | 本单按点行跳原卡，不在列表再执行；原卡仍是唯一人确认入口。 |
| 「已取消，未执行」概括旧卡 | 区分已过期、已失效、已撤回；先前步骤可能已执行的后续确认沿用「后续未执行」和结果待核对说明。 |
| 窗口顶边有较宽的计数入口、右侧面板 | 已交 B 的实际铃铛在共用侧栏，使用原生 dialog。必须在中英宽窄实现图中并排标明这个位置/容器差异；不得声称与旧图完全一致，也不自行新增第二个入口。外观仍等用户看实现图点头才合。 |

以上实现差异仍待用户看图批准。若实施时发现侧栏在某视图不可见，需在原铃铛组件范围解决可达性并单列图上差异，不能靠另建第二入口掩盖。

## 实施后的红绿与交付条件

- 红：现状无跨视图确认列表；记录提醒计数不能代表有效确认；原 pending 来源取不到失效/撤回历史。绿：只保留 1 张有效卡、混入过期/失效/撤回/被取代和记录提醒时，N 为 3（1 张有效卡、1 条记录提醒、1 条临时目录提醒）；「全部」看得到结束卡及原因。
- 用合成终端证明目标开工、新的同标题弹窗、到期边界、撤回会从有效集合移除；暂断连不判不存在。切筛选/点行写入终端零字节，有效原卡仅执行一次。
