# 待你确认：集中入口与过时卡（提案，未实现）

2026-11-15。服务愿景「一个入口，用好所有 agent」：让人找得到还有效的请求，并避免旧操作打断新工作。范围仅为已有确认请求的展示和执行校验；不新增自动确认，不改 B 的铃铛文件。

## 入口选择

| 选项 | 利弊 | 建议 |
| --- | --- | --- |
| B 正在做的小铃铛里集中列出「待你确认」，按等待时间排列，点开定位原卡 | 复用入口、跨消息流可找；需要 B 接入统一请求状态与原卡链接 | 推荐。计数只含尚可处理的请求；失效记录留在原卡可查。 |
| 侧栏另设「待你确认」 | 常驻且明显；与铃铛重复，占导航位置 | 不另建入口。 |
| 仅在大管家消息流置顶未处理卡 | 改动较小；别的会话与长消息流仍难找 | 可作过渡，不能作为集中入口的终态。 |

## 过时卡选择

| 选项 | 利弊 | 建议 |
| --- | --- | --- |
| 确认时重核操作前提 | 能阻止刚变旧的卡；每类操作须明确定义有效条件 | 必做。Esc 卡绑定目标 nativeId、连接代次、弹窗类型与本次出现标识；执行前以当前终端重核。成员已开工、弹窗已消失或换了一次，即拒绝，原卡标「已失效，未执行」，不转用为新授权。 |
| 显示请求年龄与失效原因 | 人能判断上下文；时间本身拦不住误操作 | 配合重核显示，例如「请求于 8 分钟前」。不要只靠人判断年龄。 |
| 按操作类别设置有效期 | 短期操作不会长期挂着；太短会误伤仍有效的请求，期限内也可能变旧 | volatile 终端输入可另设短有效期；低频管理请求按前提有效性保留。期限需由后续需求和实测确定，不在本单拍一个通用分钟数。 |

推荐一个后续建设项：由 B 的铃铛承接现有待确认记录，同时在确认执行边界校验该操作的有效前提。先覆盖可能打断工作的终端输入；年龄为解释，分类有效期为补充。展示样式先出图请用户看；本提案不授权实施。

## 已读实现与边界

`app/background-control.cjs` 的 `decide` 会重核请求仍为 `confirmation-required`、确认内容相同、调用者仍有效，也会拒绝已经在较新卡确认的同一请求，然后再次进入 `perform`；这不是一个完全没有校验的入口。记录有 `at`，但这里没有通用的年龄到期判定。现有身份或权限检查不能代替「这个 Esc 仍只针对刚才那个弹窗」的操作语义校验。

后续验收：在一个弹窗出现时生成 Esc 卡；先关闭弹窗并让成员开工，再点击旧卡，原生终端必须收到零输入。重新出现相同标题的另一个弹窗也不能复用旧卡。仍有效的卡只执行一次；失效卡退出铃铛计数，保留原因与原请求记录。

## 补充：任何视图可见、撤回与现存卡清理

15:31 的派单补充转述用户：「我已经找不到以前的卡了，所以不会去点了」。同一补充提供现场计数：现有 22 张待确认，当前大管家 5 张（4 张 Esc、1 张参数探测），前任发起者 17 张。本单没有读取真实卡文件或任何成员会话；此计数是提供的现场读数，执行前须重新核对。

源码核实：`background-control.cjs` 的重启恢复只把 `running` 改为 `unconfirmed`，待确认记录会保留；单发起者上限 32、全局上限 128，达到门槛会以 `confirmation-limit` 拒绝新请求。现有 22 张尚未达到全局门槛。命令目录没有撤回本人确认请求的入口。`main.cjs` 已向人的窗口投影 `backgroundConfirmations`；`renderer/activity-stream.js` 已有等待条和「全部」展开，因此应复用已有请求投影和原卡，改善入口可见性。

**推荐位置。** 在所有视图共用的窗口顶部、B 的铃铛旁持续显示「22 件等你确认」；点开同一份待确认列表。零件时显示「暂无待确认」，不新增侧栏页。列表显示发起者、目标、操作、请求年龄，回到原卡的链接为辅助。这里是对 B 入口的提案，不修改 B 的组件或样式。原型为 `confirmation-inbox-prototype.html`，两幅画面只用示例卡；实现前须用户看图同意。

**作废规则。** 所有作废都停止后续执行，移出待确认计数，保留原卡和原因，显示「已取消，未执行」。作废与执行的决策必须在同一串行边界互斥；先执行的请求不能再改写为未执行。

| 条件 | 一句利弊及推荐 |
| --- | --- |
| 发起者撤回自己的待确认卡 | 能撤掉错误或重复请求；须核对发起者身份和请求 id，只能取消自己的 pending 请求，不能撤回别人的或重放已执行操作。推荐新增明确的撤回命令。 |
| 同一请求被新卡取代 | 避免重复占位；需同时匹配发起者、动作、目标和前提，不能仅凭文字相似。推荐旧卡自动作废并链接新卡；新卡仍需人确认。 |
| 目标会话不存在或已归档 | 直接清掉不再可用的目标；后台暂时断连不等于不存在。推荐以权威名册重核，缺证据则显示「暂无法核对」，不执行、不误取消。 |
| 按种类到期 | 能控制长期堆积；短期限可能让人来不及看。建议终端 Esc/输入类 60 秒、一般管理类 10 分钟作为待批准初值；确认当下仍须重核前提，不能把期限当安全证明。 |
| 只显示年龄而不作废 | 实现轻；仍会误点失效动作。只作为说明，不单独采用。 |

Esc/输入卡额外绑定原生会话、连接代次、当次弹窗标识；成员已开始任务或弹窗已变，即使只过 1 秒也作废。发起者代际变化不转移旧授权。过期后重发是新请求，不自动延长原卡，也不自动执行。

**现存 22 张的一次性清理。** 推荐在上述入口具备取消能力后，向用户展示一次冻结清单：请求 id、发起者、目标、动作和时间，勾选这次提供的旧请求；按钮写「取消这 22 个请求，均不执行」。用户明确同意才由 NAW 的操作控制器执行逐项取消并写审计，不直接编辑 JSON、不删除记录、不发送 Esc。执行时重新核对仍在等待；已执行、已取消、发生变化或后创建的请求跳过，最后给出取消/跳过数量。名单或数量变化须刷新预览，不能悄悄把后来新增的请求一起取消。

**谁点头。** 这次只做提案和原型。实际一键清理由用户本人明确批准；大管家或作者不能把「找不到卡、不会去点」解释成清理授权。界面外观和建议有效期也须用户先决定。实现和清理均属于后续同一个「待确认入口」建设项，本单未实施。
